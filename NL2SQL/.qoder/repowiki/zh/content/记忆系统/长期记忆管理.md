## 简介
本技术文档面向NL2SQL长期记忆管理系统，系统性阐述其设计理念、三层筛选机制、LLM智能分析能力、异步存储队列机制以及配置参数与性能调优建议。长期记忆作为系统第二层能力，负责从用户查询中提取并存储偏好知识，包括查询模式、字段别名、常用指标/维度偏好等，从而提升后续意图识别与实体解析的准确性与效率。

## 项目结构
长期记忆相关模块位于后端工程的memory目录，围绕三层核心能力组织：
- 长期记忆提取与存储：负责从查询意图中提取偏好并进行存储
- 异步存储队列：将存储操作异步化，避免阻塞主流程
- 记忆维护：定期压缩、清理与相似模式合并
- 向量存储：为Schema与查询历史提供语义检索能力（辅助长期记忆）

## 架构概览
长期记忆系统采用“三层筛选 + LLM智能分析 + 异步队列”的设计，确保只存储高价值偏好，同时通过异步机制保证系统性能与稳定性。

```mermaid

participant LLM as "LLM服务"
participant MQ as "存储队列(memoryQueue)"
participant DB as "SQLite数据库"
U->>LTM : 提交查询意图
LTM->>LTM : 置信度阈值筛选(>0.7)
alt LLM启用
LTM->>LLM : 智能分析(字段别名/习惯/逻辑)
LLM-->>LTM : 分析结果(JSON)
else LLM禁用
LTM->>LTM : 逻辑判断(高价值模板/高频模式)
end
alt 存储决策通过
LTM->>MQ : 入队存储(查询模式/指标/维度/别名)
MQ->>DB : 批量异步写入
else 拒绝存储
LTM-->>U : 返回原因(低置信度/一次性查询等)
end
```

## 详细组件分析

### 三层筛选机制
系统通过三道筛选防线，确保只存储高价值偏好：
1) 置信度阈值（>0.7）：拒绝低质量意图
2) 查询模式价值评估（维度≥2且指标≥1）：高价值模板优先
3) 高频模式检测（7天内≥2次）：重复出现的模式优先

```mermaid

CheckSuccess --> |否| Reject1["拒绝: 查询失败"]
CheckSuccess --> |是| CheckConf["置信度≥0.7?"]
CheckConf --> |否| Reject2["拒绝: 置信度不足"]
CheckConf --> |是| CheckSpecific["是否过于具体(一次性)?"]
CheckSpecific --> |是| Reject3["拒绝: 一次性查询"]
CheckSpecific --> |否| EvalValue["评估存储价值"]
EvalValue --> HighVal{"高价值模板?<br/>维度≥2且指标≥1"}
HighVal --> |是| StoreHigh["存储高价值模板"]
HighVal --> |否| CheckFreq["7天内相似查询≥2次?"]
CheckFreq --> |是| StoreFreq["存储高频模式"]
CheckFreq --> |否| Observe["简单查询需更高频率"]
StoreHigh --> End(["结束"])
StoreFreq --> End

```

### LLM智能分析功能
当启用LLM智能分析时，系统使用精心设计的提示词，从用户查询中提取四类偏好：
- 字段别名（field_alias）：最高优先级，涵盖游戏实体映射、数据源映射与字段别名
- 分析习惯（dimension_habit/metric_bundle）：用户习惯的维度组合或指标集合
- 业务逻辑定义（filter_logic）：用户定义的通用过滤规则
- 通用/单次查询（standard）：低价值，不应存储

```mermaid

PARSER-->>LTM : 返回结构化结果

end
```

### 异步队列机制
内存队列采用批量处理与并发执行策略，显著提升高并发场景下的吞吐量与稳定性：
- 内存队列：先进先出，记录操作函数与上下文
- 批量处理：每次取固定数量（默认5）并发执行
- 错误处理：Promise.allSettled收集结果，失败记录日志但不影响整体流程
- 间隔调度：处理完成后延迟一段时间继续处理剩余任务

```mermaid
flowchart TD
Enqueue["入队操作"] --> CheckProc{"是否正在处理?"}
CheckProc --> |否| StartProc["启动处理循环"]
CheckProc --> |是| Wait["等待处理完成"]
StartProc --> Batch["批量取出(默认5)"]
Batch --> Parallel["并发执行Promise.allSettled"]
Parallel --> Stats["统计成功/失败数量"]
Stats --> More{"队列是否仍有任务?"}
More --> |是| Delay["延迟后继续处理"]
More --> |否| Done["处理完成"]
Delay --> StartProc
```

### 记忆维护与清理策略
系统采用分级保留策略，避免存储膨胀：
- 高频（≥10次）：永久保留
- 中频（3-9次）：90天未用清理
- 低频（<3次）：30天未用清理
- 字段别名：365天未用清理

## 性能考虑
- 异步存储：通过内存队列与批量处理，显著降低主线程阻塞
- 索引优化：user_id、preference_type、复合索引加速查询与清理
- 阈值调优：合理设置置信度阈值与频率阈值，平衡存储价值与性能
- 向量检索：智能搜索结合表名推断与优先级重排，提升检索质量
- 日志级别：生产环境建议使用info/warn/error，避免trace/debug造成I/O开销

## 故障排查指南
- LLM分析失败：系统会回退到逻辑判断，检查LLM API配置与网络连通性
- 存储失败：队列处理使用Promise.allSettled，失败记录日志但不影响整体流程
- 队列堆积：检查队列状态与处理间隔，必要时调整批量大小
- 记忆清理异常：核对保留策略配置，确认用户偏好表索引是否生效
