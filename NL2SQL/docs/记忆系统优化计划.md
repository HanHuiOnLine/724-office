## 1. Token 感知摘要触发 (P0)

### 问题描述
当前 `summarizer.js` 仅基于固定轮数（8轮）触发摘要，无法适应不同长度的对话。一轮对话可能包含 500 Token 也可能包含 5000 Token。

### 优化方案
修改触发条件，增加 Token 密度检测：

```javascript
// summarizer.js 第 457-464 行
const currentRounds = Math.floor(history.length / 2);
const historyTokens = tokenBudget.estimateObjectTokens(history);

// 触发条件：轮数 >= 8 或 Token 数 > 6000（约 60% 的 10k 预算）
const tokenThreshold = 6000;
if (currentRounds < config.triggerRounds && historyTokens < tokenThreshold) {
  return {
    compressed: false,
    history: history,
    reason: `当前 ${currentRounds} 轮/${historyTokens} tokens，未达到触发阈值`
  };
}
```

### 预期效果
- 避免长对话 Token 爆炸
- 提高摘要质量，防止上下文断层

## 2. 置顶记忆保护 (P1)

### 问题描述
`memoryMaintenance.js` 的清理逻辑过于僵化，可能删除用户明确设置的业务规则（如"以后青木都指代 game_id=30"）。

### 优化方案

#### 步骤 1: 扩展表结构
```javascript
// database.js 第 140-157 行添加字段
is_pinned INTEGER DEFAULT 0,      // 0=普通, 1=置顶
priority INTEGER DEFAULT 0,       // 0=auto, 1=manual, 2=pinned
source TEXT DEFAULT 'auto',       // auto | manual
```

#### 步骤 2: 修改清理逻辑
```javascript
// memoryMaintenance.js 第 135-165 行添加过滤条件
// 清理中频偏好(3-9次)：90天未用清理
const mediumResult = await database.run(
  `DELETE FROM user_preferences 
   WHERE user_id = ? 
   AND usage_count >= ? AND usage_count <= ?
   AND last_used_at < datetime('now', '-${CLEANUP_RULES.MEDIUM_USAGE.ttlDays} days')
   AND is_pinned = 0`,  // 跳过置顶记忆
  [userId, CLEANUP_RULES.MEDIUM_USAGE.minUsage, CLEANUP_RULES.MEDIUM_USAGE.maxUsage]
);
```

### 预期效果
- 保护关键业务规则不被误删
- 支持用户手动标记重要记忆

## 3. 异步记忆存储队列 (P1)

### 问题描述
`longTermMemory.js` 中所有存储操作都是 `await` 阻塞的，在高并发下会影响主意图识别流程性能。

### 优化方案
新增 `memoryQueue.js` 模块：

```javascript
// memoryQueue.js
const memoryQueue = [];
let isProcessing = false;

async function enqueueMemoryStore(operation) {
  memoryQueue.push(operation);
  if (!isProcessing) processQueue();
}

async function processQueue() {
  isProcessing = true;
  while (memoryQueue.length > 0) {
    const op = memoryQueue.shift();
    try {
      await op();
    } catch (err) {
      logger.error('记忆存储失败:', err);
    }
  }
  isProcessing = false;
}

module.exports = { enqueueMemoryStore };
```

修改 `longTermMemory.js` 调用方式：
```javascript
// 原代码（阻塞）
await storeUserPreference(userId, type, content);

// 新代码（非阻塞）
enqueueMemoryStore(() => storeUserPreference(userId, type, content));
```

### 预期效果
- 提升并发性能
- 主流程不再被存储操作阻塞

## 4. Schema 增量更新 (P1)

### 问题描述
`vectorStore.clearSchemaVectors` 通过重新创建表来实现清空，在 Schema 频繁变动时会导致系统抖动。

### 优化方案

#### 步骤 1: 新增增量更新方法
```javascript
// vectorStore.js 新增
const crypto = require('crypto');

async function upsertSchemaVector(tableName, text, vector, metadata) {
  const contentHash = crypto.createHash('md5').update(text).digest('hex');
  
  // 检查是否存在且未变更
  const existing = await findSchemaByTableName(tableName);
  if (existing && existing.metadata.hash === contentHash) {
    return { updated: false, reason: 'no_change' };
  }
  
  // 标记旧向量为删除（LanceDB 不支持直接删除，使用软删除标记）
  if (existing) {
    await markSchemaAsDeleted(existing.id);
  }
  
  // 添加新向量
  metadata.hash = contentHash;
  metadata.updated_at = Date.now();
  await addSchemaVectors([text], [vector], [metadata]);
  
  return { updated: true, reason: existing ? 'changed' : 'new' };
}
```

#### 步骤 2: 修改 Schema 加载逻辑
```javascript
// schemaLoader.js 第 201-281 行修改
async function vectorizeSchema() {
  // ... 现有代码 ...
  
  for (const table of schemaData.tables) {
    const tableRepresentation = buildTableRepresentation(table);
    
    // 使用增量更新替代全量重建
    await vectorStore.upsertSchemaVector(
      table.name,
      tableRepresentation.text,
      await llmService.getEmbedding(tableRepresentation.text),
      {
        type: 'table',
        name: table.name,
        scope: tableRepresentation.scope,
        data_type: tableRepresentation.dataType,
        hash: '',  // 由 upsertSchemaVector 计算
        updated_at: Date.now()
      }
    );
  }
}
```

### 预期效果
- 解决 Schema 频繁变动时的系统抖动
- 减少不必要的 Embedding API 调用
