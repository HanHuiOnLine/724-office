# NL2SQL 向量检索优化计划

## 一、现状分析

### 1.1 核心指标

| 指标 | 当前值 | 目标值 | 状态 |
|------|--------|--------|------|
| Schema 检索准确率 | 25% | ≥60% | 🔴 危险 |
| 平均语义距离 | 0.6~0.7 | ≤0.5 | 🟡 待优化 |
| 查询历史评估误差 | 0 | - | 🟢 正常 |

### 1.2 核心认知

> **NL2SQL 质量 = 表召回率 × LLM 推理能力**

**关键洞察：** 只要召回了正确的表（Table Recall），LLM 强大的 Reasoning 能力就能根据字段描述（Schema Description）自动对齐语义。

- 字段语义已由 `schema-metadata.json` 中的 `name_cn` 和 `description` 保障
- 向量检索的任务不是"选出唯一的字段"，而是**"确保正确的表在 LLM 的视线范围内"**
- 当前瓶颈：**正确的表甚至没进 Top 10**，LLM 连看到字段描述的机会都没有

### 1.3 关键问题诊断

#### A. 表级信息被碎片化（核心问题）

**现象：** 查询"注册用户"时，向量空间发生**语义稀释**，返回的是字段级别的匹配结果。

**根因：** 当前向量存储以**字段**为单位，表的信息被碎片化了：
```
搜索"注册用户" → 匹配到 channel_id 字段 → 顺带拉出 online_time_daily 表
```

这种"以字段带表"的策略，容易被包含大量通用字段（如日期、渠道、ID）的活跃报表抢占排名。

#### B. 严重的"同名异表"干扰（Schema 噪声）

**现象：** 查询"DAU"时，召回了大量 `new_tzwuxian`、`new_tzhlxxyi` 等特定游戏的日志表，而漏掉了 `tzpingtai_tz_sdk_log_pf_act`（平台通用活跃表）。

**根因：** 不同游戏的表结构高度相似，向量空间中它们极度挤压，导致检索结果被特定游戏表"霸榜"。模型无法区分**"平台通用表"**与**"具体游戏业务表"**。

#### C. 存储文本缺乏"表级特征锚点"

**现象：** 存储的文本包含大量技术术语（如 `BIGINT`、`唯一ID`），稀释了业务语义权重。

**根因：** 向量存储的 `text` 字段格式未优化，缺乏：
- 表的业务定位描述（如"平台统一注册日志"）
- 核心动作特征词（如"新增、首入"）
- 数据源类型标签（Raw Data vs Report）

## 二、优化方案

### 2.1 方案优先级矩阵

| 优先级 | 方案 | 预期效果 | 实施难度 | 预计工期 |
|--------|------|----------|----------|----------|
| P0 | 表级表征重构（核心） | ⭐⭐⭐⭐⭐ | ⭐⭐ | 2天 |
| P1 | 混合搜索 (Hybrid Search) | ⭐⭐⭐⭐ | ⭐⭐⭐ | 3天 |
| P2 | 两阶段检索 (Reranking) | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 4天 |

> **注：** 原 P3（语义增强）已删除。字段语义由 `name_cn` 保障，无需外部增强。

### 2.2 详细实施方案

---

#### P0: 表级表征重构（投入产出比最高）

**目标：** 从"字段级搜索"转向"表级表征搜索"，确保正确的表进入 Top 10

**核心策略：**
- 每个表只生成**一个表级向量**，而非多个字段向量
- 表级文本浓缩表的核心业务含义
- 添加 `scope` 和 `data_type` 元数据标签用于过滤

**实施步骤：**

1. **修改 `schemaLoader.js` - 重构文本生成逻辑**

**新文本模板格式（表级）：**
```
[域:{scope}] 表名:{table_name} ({table_cn_name})
类型:{data_type} 
功能:{business_function}
核心特征:{key_features}
```

**示例对比：**

| 查询 | 原召回（字段级） | 期望召回（表级） |
|------|------------------|------------------|
| 渠道520注册 | `new_tzpt.tzpingtai_report_new_account_online_time_daily` | `tzpingtai_tz_sdk_log_pf_reg` |
| 青木付费金额 | `new_tzqingmu.tzqingmu_log_shop` | `tzpingtai_tz_sdk_log_pf_order` |
| 按钮点击分析 | `tzpingtai_log_vst_button_click` | `tzpingtai_tz_sdk_log_button` |

**优化后的表级文本示例：**
```
[域:平台] 表名:tzpingtai_tz_sdk_log_pf_reg (平台注册表)
类型:原始日志
功能:记录用户在平台的注册行为，用于统计新增用户、渠道注册分布
核心特征:新增、首入、注册、新用户、渠道注册

[域:平台] 表名:tzpingtai_tz_sdk_log_pf_order (平台订单表)
类型:原始日志
功能:记录平台所有游戏的付费订单流水，用于统计实际成交金额
核心特征:付费、订单、流水、实际成交、real_amount

[域:报表] 表名:new_tzpt.tzpingtai_report_button_analysis (埋点分析表)
类型:聚合报表
功能:按钮点击统计的聚合报表，仅新平台支持
核心特征:埋点、统计、聚合、报表
```

2. **添加元数据标签**
   - `scope`: `platform` / `game_{name}` / `report`
   - `data_type`: `raw_log` / `aggregated_report`
   - `table_name`: 原始表名（用于匹配验证）

**验收标准：**
- [ ] 每个表只生成一个向量（而非每个字段一个向量）
- [ ] 所有表包含 `scope` 和 `data_type` 标签
- [ ] 表级文本包含强动作特征词（新增、付费、活跃等）
- [ ] 区分 Raw Data 和 Report 类型

---

#### P1: 混合搜索 (Hybrid Search)

**目标：** 结合向量相似度和全文检索，解决关键词匹配问题

**实施步骤：**

1. **启用 LanceDB 全文索引**
   ```javascript
   // 在创建表时启用 FTS
   await table.createIndex('text', {
     type: 'fts',
     use_tantivy: true
   });
   ```

2. **实现 RRF (Reciprocal Rank Fusion) 融合算法**
   ```javascript
   // 向量搜索 + 全文搜索融合
   const vectorResults = await table.search(queryVector).limit(30).execute();
   const textResults = await table.search(query, 'fts').limit(30).execute();
   
   // RRF 融合
   const fusedResults = reciprocalRankFusion(vectorResults, textResults, {
     k: 60,  // RRF 常数
     vectorWeight: 0.5,
     textWeight: 0.5
   });
   ```

3. **关键词预处理**
   - 提取查询中的业务关键词（如"注册"、"付费"、"DAU"）
   - 对关键词进行扩展（如"DAU"→"日活跃用户"）

**验收标准：**
- [ ] 全文索引创建成功
- [ ] 混合搜索接口可用
- [ ] "渠道 520"这类强特征词能准确定位

---

#### P2: 两阶段检索 (Reranking)

**目标：** 使用 Cross-Encoder 对粗排结果进行二次精排

**实施步骤：**

1. **引入 BGE-Reranker 模型**
   ```javascript
   // 使用本地或 API 方式加载 Reranker
   const reranker = new BGEReranker({
     model: 'BAAI/bge-reranker-large',
     device: 'cpu'  // 或 'cuda'
   });
   ```

2. **实现两阶段检索流程**
   ```javascript
   async function searchWithRerank(query, queryVector) {
     // 第一阶段：粗排召回 Top 30
     const candidates = await vectorStore.searchSchema(queryVector, 30);
     
     // 第二阶段：Reranker 精排
     const pairs = candidates.map(c => ({
       query: query,
       document: c.text
     }));
     const scores = await reranker.rerank(pairs);
     
     // 按重排序分数排序，返回 Top 10
     return candidates
       .map((c, i) => ({ ...c, rerankScore: scores[i] }))
       .sort((a, b) => b.rerankScore - a.rerankScore)
       .slice(0, 10);
   }
   ```

**验收标准：**
- [ ] Reranker 模型加载成功
- [ ] 精排后 Top 1 准确率提升 ≥20%
- [ ] 响应时间增加 ≤500ms

---

#### P3: 元数据过滤策略（新增）

**目标：** 利用 `scope` 和 `data_type` 标签，在检索时进行硬过滤

**实施步骤：**

1. **查询意图识别**
   ```javascript
   function detectQueryScope(query) {
     // 检测是否提到具体游戏
     const gameKeywords = ['青木', '无限', '星火', '幻灵'];
     for (const game of gameKeywords) {
       if (query.includes(game)) {
         return { scope: `game_${game}`, filter: 'game_specific' };
       }
     }
     // 默认使用平台表
     return { scope: 'platform', filter: 'platform_only' };
   }
   ```

2. **带过滤的向量搜索**
   ```javascript
   async function searchWithFilter(query, queryVector, scopeFilter) {
     return await table.search(queryVector)
       .where(`scope = '${scopeFilter}' OR data_type = 'raw_log'`)
       .limit(10)
       .execute();
   }
   ```

**验收标准：**
- [ ] 未提及游戏时，优先召回 `scope=platform` 的表
- [ ] 提及游戏时，召回对应游戏表 + 平台通用表
- [ ] 报表类表（`data_type=aggregated_report`）排名降低

---

#### P4: 更换 Embedding 模型（备选方案）

**目标：** 如果上述优化后准确率仍低于 60%，升级 Embedding 模型

**候选模型：**

| 模型 | 维度 | 特点 | 适用场景 |
|------|------|------|----------|
| text-embedding-3-large | 3072 | OpenAI 最新，性能强 | 通用场景 |
| BAAI/bge-large-zh-v1.5 | 1024 | 中文优化，开源 | 中文为主 |
| BAAI/bge-m3 | 1024 | 多语言，支持长文本 | 多语言混合 |

**实施步骤：**
1. 重新生成所有 Schema 向量
2. 更新向量维度配置
3. 对比评估新旧模型效果

## 五、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| LanceDB 版本不支持 FTS | 高 | 评估升级 LanceDB 或更换向量数据库 |
