# NL2SQL 后端架构审查与优化方案

## Context

本项目是 NL2SQL 自然语言提数工具，后端约 **15,000+ 行 JavaScript**，分布在 22 个源文件中。随着 4 阶段 Agentic 工作流（Schema 探索 → 意图拆解 → 澄清 → 生成修复）的逐步引入，代码复杂度快速增长，核心文件 `nl2sqlEngine.js` 已膨胀到 2722 行。本次审查从全局架构到模块细节，识别设计缺陷并给出可落地的优化建议。

---

### 架构优点（应保留）
- **4 阶段 Agentic 工作流** 清晰分层，每个 Phase 职责明确
- **分层 Schema 访问**（Level 1 索引 / Level 2 详情）有效控制 Token 消耗
- **Feature Flags 渐进式发布**，支持快速回滚
- **启动顺序正确**，无初始化竞态条件
- **优雅关停** 处理完善（SIGTERM/SIGINT → 关闭 HTTP → 停止 Cron → 关闭数据库）

## 二、问题分析与优化建议

### P0 - 立即修复（存在运行时风险）

#### P0-1: memoryMaintenance.js SQL 字符串拼接
**问题**: `backend/src/memory/memoryMaintenance.js` 第 139/151/163 行，TTL 天数通过模板字符串直接嵌入 SQL：
```js
AND last_used_at < datetime('now', '-${CLEANUP_RULES.MEDIUM_USAGE.ttlDays} days')
```
虽然当前值来自常量（90/30/365），但建立了危险模式，且违反参数化查询最佳实践。

**修复**: 在 JS 层计算截止日期，作为参数传入：
```js
const cutoff = new Date(Date.now() - ttlDays * 86400000).toISOString();
// WHERE last_used_at < ? AND is_pinned = 0
```
涉及第 139、151、163 行共 3 处。

---

#### P0-2: 启动时未调用配置校验
**问题**: `config.js` 导出了 `validateConfig()` 函数，但 `app.js` 的 `initialize()` 从未调用。服务可以在缺少 `LLM_API_KEY` 或 `SR_DATABASE_URL` 的情况下启动，到用户查询时才报错。

**修复**: 在 `app.js` 第 103 行（步骤 1 之前）添加：
```js
config.validate();  // 开发环境 warn，生产环境 exit(1)
```

---

#### P0-3: Logger traceContext 内存泄漏
**问题**: `logger.js` 第 330 行 `startTrace()` 向 `this.traceContext`（Map）写入条目，第 405 行 `endTrace()` 删除。虽然 `nl2sqlEngine.processQuery()` 的 catch 块正确调用了 `endTrace`，但其他调用方（如 `agenticEngine`）若异常路径未清理，条目将永久泄漏。长时间运行的生产进程中，这是无界内存增长。

**修复**: 在 `startTrace` 中记录 `createdAt` 时间戳，添加定时清理（每 5 分钟清除超过 10 分钟的僵尸条目），或设置 Map 最大容量（如 500 条）。

**问题**: `routes.js`（1036 行）混合了 7 种不同领域的路由。

#### P2-2: 修正中文 Token 估算
**问题**: `tokenBudget.js:24` 使用固定 `TOKEN_RATIO = 3.5`（字符/Token）。英文约 4 字符/Token 尚可，但中文约 1.5-2 字符/Token。项目用户查询和 Schema 描述以中文为主，Token 预算可能被 **低估 40-50%**，导致上下文窗口溢出。

**方案**:
```js
function estimateTokens(text) {
  const cjkChars = (text.match(/[\u4e00-\u9fff\u3000-\u303f\uff00-\uffef]/g) || []).length;
  const otherChars = text.length - cjkChars;
  return Math.ceil(cjkChars / 1.5 + otherChars / 4);
}
```
比率可配置化放入 `config.js`。这个修改方向更保守（估算值更高 → 更早触发压缩），比低估安全得多。

---

#### P2-3: longTermMemory LLM 调用限流
**问题**: `longTermMemory.js:174` 对每次成功查询调用 `llmService.simpleChat()` 提炼偏好，无速率限制或缓存。相同查询重复触发 LLM 调用，浪费 API 额度。

**方案**:
1. 基于 `hash(query + intent)` 的内存缓存，5 分钟 TTL
2. 每用户速率限制：30 秒内最多 1 次偏好提炼
3. 利用已有的 `memoryQueue.js` 批量处理

---

#### P2-4: vectorStore 按表名查找优化
**问题**: `vectorStore.js:753` 的 `findSchemaByTableName()` 用零向量搜索 1000 条后在应用层过滤，O(N) 全扫描。

**方案**: Schema 向量化时同步建立内存 Map（`tableName → record`），直接 O(1) 查找。`upsertSchemaVector` 时刷新缓存。

#### P2-5: 解耦 sseHandler 与 nl2sqlEngine
**问题**: `sseHandler.js` 第 20 行直接 `require('./nl2sqlEngine')`，无法独立测试，也无法动态切换 legacy/agentic 引擎。

#### P2-6: vectorStore 软删除清理
**问题**: `vectorStore.js:783` 的 `markSchemaAsDeleted()` 仅打日志标记，实际从未删除。被标记的记录永久占用向量索引空间。

## 五、核心流程深度分析：长期记忆注入 & 表格检索准确性

> 以下两个问题直接影响 SQL 生成质量和 Token 消耗效率，属于核心链路优化。

### 问题 A: generateSQL 全量加载用户长期记忆

#### 现状分析

**长期记忆在两个阶段被独立加载：**

| 阶段 | 调用位置 | 加载内容 | 限制 |
|------|---------|---------|------|
| `analyzeIntent` (line 911) | `longTermMemory.getUserPreferencesForIntent(userId)` | patterns(top5) + **全部aliases** + metrics(top10) + dimensions(top10) | aliases 在展示时截断到 15 条，但有优先级排序 |
| `generateSQL` (line 1719) | `database.getFieldAliases(userId)` | **全部 field_alias 类型偏好** | **无任何限制**，按 usage_count DESC |

**问题根源：**

1. **`generateSQL` 的 `getFieldAliases(userId)` 没有任何 limit**（`database.js:713-733`）。SQL 是 `SELECT * FROM user_preferences WHERE user_id = ? AND preference_type = 'field_alias' ORDER BY usage_count DESC`，随着用户使用系统，别名积累会无限增长。

2. **两阶段重复加载**：`analyzeIntent` 已经用优先级排序展示了 15 条相关别名，但 `generateSQL` 又独立加载了全量别名，且没有考虑与当前查询的相关性。

3. **Prompt 膨胀**：每条别名生成 1-2 行文本（约 40-80 字符），100 条别名就会产生 ~4000-8000 字符（约 2000-4000 token），严重挤占 Schema 和推理规则的 Token 空间。

4. **无关信息干扰 LLM**：当用户查"昨天注册用户数"时，Prompt 中混入了大量不相关的游戏名/渠道映射，增加 LLM 的噪音，降低 SQL 生成准确率。

#### 数据流追踪

```
analyzeIntent（意图识别阶段）:
  └── getUserPreferencesForIntent(userId)
        ├── getTopQueryPatterns(userId, 5)       → 最多 5 条
        ├── getFieldAliases(userId)              → ⚠️ 无限制
        ├── getUserPreferences('metric', 10)     → 最多 10 条
        └── getUserPreferences('dimension', 10)  → 最多 10 条
      → Prompt 中展示时：优先当前查询相关 + 游戏别名，截断到 15 条 ✓

generateSQL（SQL 生成阶段）:
  └── database.getFieldAliases(userId)           → ⚠️ 无限制，全量注入
      → Prompt 中直接拼接全部别名                   → ❌ 无过滤无截断
```

#### 优化方案

**方案一：相关性过滤 + 分层加载（推荐）**

核心思想：只将**与当前查询相关的**别名注入 Prompt，分为"精确命中"和"高频常用"两层。

```js
// generateSQL 中替换当前的全量加载逻辑（line 1717-1747）
async function getRelevantFieldAliases(userId, intent, query) {
  const allAliases = await database.getFieldAliases(userId);
  const queryLower = query.toLowerCase();
  
  // 第 1 层：精确命中 — 查询中直接提到的别名（如用户说了"青木"）
  const exactHits = allAliases.filter(a => 
    queryLower.includes(a.content.user_term.toLowerCase())
  );
  
  // 第 2 层：意图关联 — 与 intent.filters 中字段相关的别名
  const intentFields = new Set(
    (intent.filters || []).map(f => f.field)
  );
  const intentHits = allAliases.filter(a => 
    !exactHits.includes(a) && 
    (intentFields.has(a.content.schema_field) || 
     intentFields.has(a.content.field_type))
  );
  
  // 第 3 层：高频兜底 — 使用次数最高的几条（已按 usage_count DESC）
  const used = new Set([...exactHits, ...intentHits].map(a => a.id));
  const highFreq = allAliases
    .filter(a => !used.has(a.id))
    .slice(0, 5);
  
  // 合并，总数上限 20 条
  return [...exactHits, ...intentHits, ...highFreq].slice(0, 20);
}
```

**方案二：数据库层限制 + 查询条件下推**

在 `database.getFieldAliases` 增加可选参数：

```js
async function getFieldAliases(userId, { limit = 50, userTerms = [] } = {}) {
  let sql = `SELECT * FROM user_preferences 
    WHERE user_id = ? AND preference_type = 'field_alias'`;
  const params = [userId];
  
  // 如果提供了关键词，优先匹配
  if (userTerms.length > 0) {
    const placeholders = userTerms.map(() => '?').join(',');
    sql += ` ORDER BY 
      CASE WHEN json_extract(content, "$.user_term") IN (${placeholders}) 
        THEN 0 ELSE 1 END,
      usage_count DESC`;
    params.push(...userTerms);
  } else {
    sql += ' ORDER BY usage_count DESC';
  }
  
  sql += ' LIMIT ?';
  params.push(limit);
  
  return query(sql, params).then(rows => 
    rows.map(a => ({ ...a, content: JSON.parse(a.content) }))
  );
}
```

**方案三：复用 analyzeIntent 结果，消除重复加载**

`analyzeIntent` 已经做了智能筛选（15 条优先级排序的别名），在 `processQuery` 中将结果传递给 `generateSQL`，避免二次查库：

```js
// processQuery 中（line ~2239）
const intent = await analyzeIntent(userQuery, recentHistory, userId);
// intent 已包含 resolvedAliases（在 analyzeIntent 中附加）

// generateSQL 中直接使用
const fieldAliases = intent._resolvedAliases || [];  // 由 analyzeIntent 传递
```

**推荐组合**：方案一（相关性过滤） + 方案三（复用结果），既保证精准又避免重复查询。

### 问题 B: getRelevantTablesForIntent 返回不准确

#### 现状分析

**Schema 规模**：456 张表，分属 13 个游戏库 + 平台库 + DWD 聚合库。各游戏表通过游戏名关键词（如 `xinghuo`/`qingmu`/`hlxxyi`）和中文描述（如"星火游戏订单表（game_id=40）"）互相之间可区分。

```
表分布（456 张）:
  不含 new_ 前缀（核心平台 + DWD）   → 48 张
    ├── tzpingtai_tz_sdk_* (SDK 核心) → 18 张  ← 覆盖 80%+ 通用查询
    ├── tzpingtai_其他                → 14 张
    └── dwd_* (聚合报表)             → 16 张
  含 new_ 前缀（各数据库下的表）      → 408 张
    ├── new_tzpingtai.* (新平台库)    → 34 张

```

**核心问题链：**

**1. scope 分类逻辑有 bug — 140 张表被错误归为 `platform`**

`buildTableRepresentation()`（`schemaLoader.js:298`）的 scope 判断：
```js
if (tableName.includes('tzpingtai') || tableName.includes('pf_')) {
  scope = 'platform';
} else if (tableName.startsWith('new_tz')) { ... }
```

`tableName.includes('tzpingtai')` 这个条件**过于宽泛**。由于 `if...else if` 结构，`new_tzpingtai.*` 和 `new_tzpingtaiold.*` 表名中都包含 `tzpingtai`，会命中第一个 `if` 而**跳过** `else if`，导致它们全部被归为 `scope=platform`。

实际 scope=platform 的 **140 张表**构成：

| 分类 | 数量 | 真实性质 | 应有 scope |
|------|------|---------|-----------|
| SDK 核心 (`tzpingtai_tz_sdk_*`) | 18 | 平台通用表，最高优先级 | `platform_core` |
| 平台其他 (`tzpingtai_log_*` 等) | 14 | 平台日志/埋点 | `platform_other` |
| DWD 平台 (`dwd_tzpingtai_*`) | 11 | 报表聚合 | `report` |
| **`new_tzpingtai.*`（新平台库）** | **34** | 需用户指定"新平台"才使用 | `platform_newdb` |
| **`new_tzpingtaiold.*`（老平台库）** | **30** | 需用户指定"老平台"才使用 | `platform_olddb` |
| 报表库/外部表 (`new_tzpt.*` 等) | 33 | 混杂 | `report` / `external` |

**直接后果**：当用户问"查注册用户数"（未指定游戏），`searchSchemaSmart` 给所有 `scope=platform` 的表加 +50 分。**140 张表都拿到平台加分**，其中 `new_tzpingtai.tzpingtai_tz_sdk_log_pf_order` 和真正的核心表 `tzpingtai_tz_sdk_log_pf_order` 在向量距离和加分上几乎完全相同。LLM 收到混乱的候选表列表，SQL 生成准确率下降。

**向量表征对比验证**：
```
平台注册: [域:platform] 表名:tzpingtai_tz_sdk_log_pf_reg (平台注册表) ... 核心特征:注册、新增
星火注册: [域:game_xinghuo] 表名:new_tzxinghuo.tzxinghuo_log_register (星火游戏注册账号（game_id=40）) ... 核心特征:注册、新增
新平台注册: [域:platform] 表名:new_tzpingtai.tzpingtai_tz_sdk_log_game_reg (...) ... 核心特征:注册、新增
                  ↑ 与核心表同 scope、同特征，无法区分
```

**2. 重排序游戏名检测只硬编码了 7 个**

`searchSchemaSmart()`（`vectorStore.js:461`）：
```js
const gameKeywords = ['青木', '无限', '星火', '幻灵', 'tzqingmu', 'tzwuxian', 'tzxinghuo'];
```
遗漏了幻灵系列变体（DD/F/GF/HB）、老平台、报表库等，且无法随 Schema 变更自动更新。

**3. 表检索执行两次，策略不一致**

| 调用 | 位置 | topK | 上下文 | 用途 |
|------|------|------|--------|------|
| 第 1 次 | `analyzeIntent` line 892 | 10 | 无 | 提供表名列表给 LLM 做意图识别 |
| 第 2 次 | `generateSQL` line 1627 | 3 | 有 gameId/datasource | 提供 Schema 详情给 LLM 写 SQL |

第 1 次检索**没有任何业务上下文**（此时意图尚未识别），完全依赖向量相似度 + 有 bug 的 scope 加权，是准确率最低的一次。而它的结果直接影响 LLM 的意图识别质量。

**4. 关键词兜底策略固定**

`getCoreHighFrequencyTables()`（line 158-177）硬编码了 13 张"核心高频表"，不随实际使用频率调整，且混入了游戏表（如 `tzqingmu_log_game_user_chat`）。

#### 优化方案

**修改一（立即生效）：修复 scope 分类逻辑** — `schemaLoader.js` `buildTableRepresentation`

将 `platform` 细分为 5 个层级，关键是**先判断 `new_` 前缀再判断内容**：

```js
function buildTableRepresentation(table) {
  const tableName = table.name;
  let scope = 'unknown';

  // 1. 先判断是否是特定数据库下的表（new_xxx.yyy 格式）
  if (tableName.startsWith('new_')) {
    const dbMatch = tableName.match(/^new_(\w+?)\./);
    if (dbMatch) {
      const dbName = dbMatch[1];
      if (dbName === 'tzpingtai')          scope = 'platform_newdb';   // 新平台库
      else if (dbName === 'tzpingtaiold')  scope = 'platform_olddb';   // 老平台库
      else if (dbName === 'external_tables') scope = 'external';
      else if (dbName === 'tzpt' || dbName === 'tzbigdata_dm') scope = 'report';
      else scope = 'game_' + dbName.replace(/^tz/, '');  // 游戏库
    }
  }
  // 2. 非 new_ 前缀的表
  else if (tableName.startsWith('dwd_'))                 scope = 'report';
  else if (tableName.startsWith('tzpingtai_tz_sdk_'))    scope = 'platform_core';  // SDK 核心
  else if (tableName.startsWith('tzpingtai_'))           scope = 'platform_other';

  // ...rest unchanged
}
```

> 此修改需要 `SCHEMA_REVECTORIZE=true` 重启后生效（scope 嵌入在向量元数据中）。

**修改二（立即生效）：分层加权重排序** — `vectorStore.js` `searchSchemaSmart`

替换原来统一的 `+50 platform` 为分层策略：

```js

  switch (metadata.scope) {
    case 'platform_core':   priorityScore += 80; break;  // SDK 核心表
    case 'platform_other':  priorityScore += 50; break;  // 平台其他
    case 'report':          priorityScore += 40; break;  // DWD 报表

    case 'platform_olddb':  priorityScore += 10; break;  // 老平台库（需指定"老平台"）
    default:

}
```

**修改三（立即生效）：从 Schema 动态构建游戏名索引** — `schemaLoader.js` 新增

替代 `searchSchemaSmart` 中硬编码的 7 个游戏名：

```js
// 启动时从 schema-metadata.json 自动提取
function buildGameNameIndex() {
  const gameIndex = new Map(); // 中文游戏名 → { prefix, gameId }

  for (const table of schemaData.tables) {
    if (!table.name.startsWith('new_tz')) continue;
    const dbMatch = table.name.match(/^new_(\w+?)\./);
    if (!dbMatch) continue;

    const prefix = dbMatch[1];
    const nameCn = table.name_cn || '';

    // 从 "星火游戏订单表（game_id=40）" 提取 "星火" 和 "40"
    const gameNameMatch = nameCn.match(/^(.+?)游戏/);
    const gameIdMatch = nameCn.match(/game_id=(\d+)/);

    if (gameNameMatch && !gameIndex.has(gameNameMatch[1])) {
      gameIndex.set(gameNameMatch[1], {
        prefix,
        gameId: gameIdMatch ? gameIdMatch[1] : null
      });
    }
  }
  return gameIndex;
  // → Map { '星火' => {prefix:'tzxinghuo', gameId:'40'},
  //         '青木' => {prefix:'tzqingmu', gameId:'30'},
  //         '幻灵1' => {prefix:'tzhlxxyi', gameId:'8'}, ... }
}
```

在 `searchSchemaSmart` 中替换硬编码：
```js
// 替换 line 461 的硬编码 gameKeywords

let mentionedGame = null;
for (const [gameName, info] of gameNameIndex) {

    break;
  }
}
```

### 问题 C: schema-metadata.json 向量化数据质量

#### 评估数据（来自系统评估页面）

| 指标 | 值 | 含义 |
|------|-----|------|
| Schema 向量命中率 | 100% | 向量检索能找到结果 |
| **精确匹配率** | **0%** | **Top-1 不是正确的表** |
| 平均匹配距离 | 0.27 | 向量距离适中 |
| 平均精确率 | 63% | 返回结果中约 6 成相关 |
| **平均 F1 分数** | **0.38** | **综合准确率很低** |

结论：**向量能检索到结果，但排序完全不对** — 正确的表混在大量相似表中无法脱颖而出。

#### 根因分析：向量化输入数据的 3 个致命短板

**短板 1：schema-metadata.json 元数据太薄**

表级只有 4 个字段：`name`、`name_cn`、`description`、`fields`

```
缺失的关键元数据:
  ✗ business_keywords  — 无业务关键词
  ✗ category           — 无表分类
  ✗ tags               — 无标签
  ✗ usage_frequency    — 无使用频率
  ✗ importance         — 无重要性等级
  ✗ relationships      — 无表关系
  ✗ sample_queries     — 无示例查询
```

`schema-metadata.example.json` 中定义了这些字段，但实际数据文件中**全部缺失**。这意味着 `buildTableRepresentation` 只能依赖表名模式匹配（`includes('reg')` → "注册"）来生成特征词，缺乏真正的业务语义。

**短板 2：description 和 name_cn 质量差异巨大**

| 质量 | 数量 | 占比 | 示例 |
|------|------|------|------|
| 无描述 | 0 | 0% | — |
| 短描述 (<10 字) | 19 张 | 4% | `dwd_role_order_di` → "角色付费表" |
| 中描述 (10-30 字) | 214 张 | 47% | `new_tzxinghuo.tzxinghuo_log_order` → "星火游戏订单表（game_id=40）" |
| 长描述 (>30 字) | 223 张 | 49% | `tzpingtai_tz_sdk_log_pf_order` → "平台订单表，记录所有支付成功的订单明细，是核心流水表" |

短描述的 DWD 表（如"订单表"、"注册表"）向量表征极度贫乏，无法与同功能的其他表区分。

**短板 3：16 组 name_cn 完全重复**

最严重的是 **16 张表 name_cn 都叫"埋点数据"**（幻灵系列 4 个版本 × 4 种活动类型）。向量化后它们的表征文本几乎完全相同，在向量空间中重叠在一起，拉低整体检索质量。

其他重复：`"答题"` 8 张、`"第一版内嵌小游戏的"` 8 张、`"充值"` 4 张 等。

**短板 4：当前 `buildTableRepresentation` 未利用字段信息构建语义差异**

6567 个字段中 45.7% 有有效描述，但向量化文本只提取了基于表名模式的特征词（`reg → 注册`），**完全没有利用字段的具体名称和描述来构建表的独特性**。

例如：`real_amount`（实际金额）字段只出现在 26 张表中 — 这是强区分信号，但当前向量化完全忽略了。

**优化二：向量表征文本融入关键字段信息（代码层面）**

在 `buildTableRepresentation` 中，将**高区分度字段**纳入表征文本：

```js
function buildTableRepresentation(table) {
  // ...existing scope/dataType/features logic...
  
  // 新增：提取高区分度字段
  const distinctiveFields = extractDistinctiveFields(table);
  
  // 新增：利用 business_keywords（如果有）
  const keywords = (table.business_keywords || []).join('、');
  
  // 新增：利用 usage_scenarios（如果有）
  const scenarios = (table.usage_scenarios || []).join('；');
  
  const text = [
    `${domainTag}[域:${scope}]`,
    `表名:${tableName} (${tableCnName})`,
    `类型:${dataType}`,
    `功能:${description}`,
    keywords ? `业务关键词:${keywords}` : '',
    scenarios ? `使用场景:${scenarios}` : '',
    `核心特征:${keyFeatures.join('、')}`,
    `关键字段:${distinctiveFields}`
  ].filter(Boolean).join(' ');
  
  return { text, scope, dataType, keyFeatures };
}

function extractDistinctiveFields(table) {
  const fields = table.fields || [];
  
  // 选择高区分度字段（非通用字段）
  const commonFields = new Set([
    'sf_id', 'create_time', 'game_id', 'channel_id',
    'tz_account_id', 'role_id', 'tz_server_id', 'tz_cross_id'
  ]);
  
  const distinctive = fields
    .filter(f => !commonFields.has(f.name))
    .slice(0, 5)  // 最多取 5 个
    .map(f => f.name_cn || f.name);
  
  return distinctive.join('、');
}
```

**效果**：核心平台订单表的表征文本会包含 `关键字段:实际金额、订单金额、商品名称、支付类型、订单状态`，这些字段在游戏订单表中可能叫不同名字或不存在，从而在向量空间中拉开距离。

### 问题 D: 长期记忆系统数据质量与去重失效

#### 现状数据（来自长期记忆管理页面 + SQLite 查询）

| 类型 | 数量 | 使用≤1次 | 问题 |
|------|------|---------|------|
| field_alias | 25 条 | 21 条 | 有 1 条错误映射、有冗余 `_value` 后缀记录 |
| metric_preference | 27 条 | **27 条 (100%)** | **只有 3 种指标，重复 9 倍** |
| dimension_preference | 18 条 | **18 条 (100%)** | **只有 2 种维度，重复 9 倍** |
| query_pattern | 1 条 | 1 条 | 正常 |

**71 条记忆中，有效不重复的仅约 25 条（去重率 65%）。**

#### 根因分析

**Bug 1（致命）：`findExistingPreference` 不支持 metric/dimension 去重**

`database.js:742-762` 的 `findExistingPreference` 函数：
```js
if (type === 'query_pattern') {
  // 按 $.name 去重 ✓
} else if (type === 'field_alias') {
  // 按 $.user_term 去重 ✓
} else {
  return null;  // ← metric_preference 和 dimension_preference 直接返回 null！
}
```

`storeMetricPreference`（line 675）调用 `findExistingPreference(userId, 'metric_preference', metric)`，但函数对 `metric_preference` 类型**直接返回 null**，永远认为"不存在"，于是每次都创建新记录。同理 `storeDimensionPreference`。

这就是为什么"收入金额"出现 8 次、"玩家账号ID"出现 9 次 — **每次查询都创建新记录，永远不走 `updatePreferenceUsage` 路径**。

**Bug 2：metric/dimension 无条件存储，不受 LLM 分析控制**

`extractAndStorePreferences`（line 420-446）中，步骤 5-6 的 metric/dimension 存储**独立于 LLM 分析结果**：

```
流程:
  1. 前置过滤（成功+置信度+非一次性） → 通过
  2. LLM分析 → shouldStore: false → return ← 此时跳过 metric/dimension
  3. LLM分析 → shouldStore: true → 存储 LLM 提取的偏好
  4. 逻辑判断路径 → 无论结果如何都继续
  5. ⚠️ 存储 intent.metrics 中的每个指标（不受4的结果控制）
  6. ⚠️ 存储 intent.dimensions 中的每个维度（不受4的结果控制）
```

当 LLM 分析 `shouldStore: true` 时（步骤 3），代码不会 return，继续执行步骤 5-6。这意味着**每次 LLM 认为值得存储的查询**，其 metrics 和 dimensions 都会被无条件地重复存入。

**Bug 3：field_alias 存在错误和冗余记录**

实际数据中的问题：

| 记录 | 问题 |
|------|------|
| `"老平台" → datasource [filter]` (用:4) | **映射错误** — 应映射到 `new_tzpingtaiold [datasource]`，而非 `datasource [filter]` |
| `"青木" → game_id [game]` (用:1) | **冗余** — 已有 `"青木" → 30 [game]` (用:5)，这条额外映射是 game_id 字段名而非值 |
| `"青木_value" → 30 [game_value]` (用:4) | **冗余** — 双记录格式遗留，与 `"青木" → 30 [game]` 重复 |
| `"新平台_value" → new_tzpingtai [datasource_value]` (用:1) | **冗余** — 与 `"新平台" → new_tzpingtai [datasource]` 重复 |
| `"老平台_value" → new_tzpingtaiold [datasource_value]` (用:1) | 唯一正确的老平台映射，但以 `_value` 格式存储 |

**Bug 4：`isTooSpecific` 过滤条件过严**

必须**同时满足** 3 个条件才过滤（具体 filters + 绝对时间 + 简单查询）。实际中绝大多数查询不会同时满足，导致几乎所有查询都通过过滤进入存储流程。

#### 优化方案

**修复一（紧急）：`findExistingPreference` 支持 metric/dimension 去重**

```js
async function findExistingPreference(userId, type, contentKey) {
  let sql;
  let params = [userId, type];

  if (type === 'query_pattern') {
    sql = `SELECT * FROM user_preferences 
      WHERE user_id = ? AND preference_type = ?
      AND json_extract(content, "$.name") = ?`;
    params.push(contentKey);
  } else if (type === 'field_alias') {
    sql = `SELECT * FROM user_preferences 
      WHERE user_id = ? AND preference_type = ?
      AND json_extract(content, "$.user_term") = ?`;
    params.push(contentKey);
  } else if (type === 'metric_preference' || type === 'dimension_preference') {
    // ← 新增：按 field_name 去重
    sql = `SELECT * FROM user_preferences 
      WHERE user_id = ? AND preference_type = ?
      AND json_extract(content, "$.field_name") = ?`;
    params.push(contentKey);
  } else {
    return null;
  }
  // ...rest unchanged
}
```

修复后：已有"收入金额"时不再创建新记录，而是 `updatePreferenceUsage` 增加 usage_count。

**修复二：清理已有重复数据**

在 `database.js` 的 `runMigrations` 中添加一次性清理：

```js
// 清理重复的 metric_preference 和 dimension_preference
// 保留每个 (user_id, preference_type, field_name) 组合中 id 最小的那条
await run(`
  DELETE FROM user_preferences 
  WHERE id NOT IN (
    SELECT MIN(id) FROM user_preferences 
    WHERE preference_type IN ('metric_preference', 'dimension_preference')
    GROUP BY user_id, preference_type, json_extract(content, '$.field_name')
  )
  AND preference_type IN ('metric_preference', 'dimension_preference')
`);
```

**修复三：修复老平台映射错误 + 清理冗余 `_value` 记录**

```js
// 1. 修正老平台映射
await run(`
  UPDATE user_preferences SET content = json_set(content, 
    '$.schema_field', 'new_tzpingtaiold',
    '$.field_type', 'datasource')
  WHERE preference_type = 'field_alias'
  AND json_extract(content, '$.user_term') = '老平台'
  AND json_extract(content, '$.schema_field') = 'datasource'
`);

// 2. 清理 _value 后缀冗余记录（已有直接映射的情况下）
await run(`
  DELETE FROM user_preferences 
  WHERE preference_type = 'field_alias'
  AND json_extract(content, '$.user_term') LIKE '%_value'
`);

// 3. 清理 "青木" → "game_id" 的冗余映射
await run(`
  DELETE FROM user_preferences 
  WHERE preference_type = 'field_alias'
  AND json_extract(content, '$.user_term') = '青木'
  AND json_extract(content, '$.schema_field') = 'game_id'
`);
```

**修复四：metric/dimension 存储增加价值判断**

当前 `extractAndStorePreferences` 步骤 5-6 对每个 metric/dimension 无条件入库。应增加过滤：

```js
// 步骤 5：存储指标偏好（增加过滤）
if (intent.metrics && intent.metrics.length > 0) {
  // 过滤掉 LLM 自动补充的通用指标（如 "收入金额" 每次都出现）
  const commonMetrics = new Set(['收入金额']); // 可配置
  const valuableMetrics = intent.metrics.filter(m => !commonMetrics.has(m));
  
  for (const metric of valuableMetrics) {
    memoryQueue.enqueueMemoryStore(
      () => storeMetricPreference(userId, metric, originalQuery),
      { type: 'metric_preference', userId }
    );
  }
}
```

或者更好的方案 — **只有 LLM 判断为个人偏好时才存储 metric/dimension**：

```js
// 如果 LLM 已经提取了偏好，不再重复存储 metric/dimension
if (!llmAnalysis) {
  // 仅在逻辑判断路径中才存储 metric/dimension
  // 且去重后再存
  for (const metric of intent.metrics || []) {
    memoryQueue.enqueueMemoryStore(
      () => storeMetricPreference(userId, metric, originalQuery),
      { type: 'metric_preference', userId }
    );
  }
}
```

**修复五：放宽 `isTooSpecific` 过滤 + 增加频率门槛**

```js
function isTooSpecific(intent) {
  // 原逻辑：三个条件都满足才过滤（过严）
  // 新逻辑：任意两个条件满足即过滤
  const conditions = [
    // 有具体数值型 filters
    intent.filters?.some(f => f.value && !isNaN(Number(f.value))),
    // 有绝对时间范围
    intent.time_range?.type === 'absolute',
    // 简单查询（维度+指标都≤1）
    (!intent.dimensions || intent.dimensions.length <= 1) &&
      (!intent.metrics || intent.metrics.length <= 1)
  ].filter(Boolean).length;

  return conditions >= 2;  // 任意 2 个满足即过滤
}
```
